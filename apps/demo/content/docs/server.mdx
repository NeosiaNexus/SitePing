`@siteping/server` turns any [store](/docs/adapters) into the HTTP API the widget and the dashboard talk to. It speaks the Fetch API only (`Request` → `Response`) and imports no Node built-in, so the same handler runs on Node 20+, Bun, Deno and edge workers, mounted by Next.js, Hono, Express or anything else.

```bash
npm i @siteping/server
```

On Prisma, [`@siteping/adapter-prisma`](/docs/adapters/prisma) gives you this handler with the Prisma store built in — every option below works there too.

## Mounting

`createSitepingHandler` returns one handler per HTTP method: `GET`, `POST`, `PATCH`, `DELETE` and `OPTIONS`. Mount all five on a single URL.

### Next.js (App Router)

```ts
// app/api/siteping/route.ts
import { createSitepingHandler } from "@siteping/server";
import { store } from "@/lib/siteping-store";

export const { GET, POST, PATCH, DELETE, OPTIONS } = createSitepingHandler({
  store,
  apiKey: process.env.SITEPING_API_KEY,
});
```

### Hono

```ts
import { createSitepingHandler } from "@siteping/server";
import { Hono } from "hono";
import { store } from "./siteping-store";

const siteping = createSitepingHandler({ store, apiKey: process.env.SITEPING_API_KEY });

const app = new Hono();
app.on(["GET", "POST", "PATCH", "DELETE", "OPTIONS"], "/api/siteping", (c) => {
  // Hono runs GET routes for HEAD too, a method SitePing does not serve.
  const handle = siteping[c.req.method as keyof typeof siteping];
  return handle ? handle(c.req.raw) : c.body(null, 405, { Allow: "GET, POST, PATCH, DELETE, OPTIONS" });
});

export default app;
```

`Bun.serve`, `Deno.serve` and a Cloudflare Worker's `fetch` hand you every request, whatever its method — `HEAD` from an uptime monitor, `PUT`, anything: look the handler up among the five, and answer `405` to the rest:

```ts
const METHODS = ["GET", "POST", "PATCH", "DELETE", "OPTIONS"] as const;

function handleSiteping(request: Request): Response | Promise<Response> {
  const method = METHODS.find((name) => name === request.method);
  if (!method) return new Response(null, { status: 405, headers: { Allow: METHODS.join(", ") } });
  return siteping[method](request);
}

Bun.serve({ fetch: handleSiteping });
```

Remix and SvelteKit endpoints export a function per method: have each call its own, `siteping.GET` from the `GET`.

### Express

Express hands you Node's `req`/`res`, not a `Request`: convert at the edge.

```ts
import { createSitepingHandler, type SitepingHandler } from "@siteping/server";
import express from "express";
import { store } from "./siteping-store";

const siteping = createSitepingHandler({ store, apiKey: process.env.SITEPING_API_KEY });
const app = express();

// Raw bytes in: the handler parses and validates the JSON itself. Screenshots
// travel inline, so allow the handler's own cap (maxBodyBytes), not body-parser's 100 kB.
app.all("/api/siteping", express.raw({ type: () => true, limit: "4mb" }), async (req, res) => {
  const handle = siteping[req.method as keyof SitepingHandler];
  if (!handle) {
    res.set("Allow", "GET, POST, PATCH, DELETE, OPTIONS").sendStatus(405);
    return;
  }
  const headers = new Headers();
  for (const [name, value] of Object.entries(req.headers)) {
    if (value !== undefined) headers.set(name, Array.isArray(value) ? value.join(", ") : value);
  }
  const response = await handle(
    new Request(`${req.protocol}://${req.get("host")}${req.originalUrl}`, {
      method: req.method,
      headers,
      body: Buffer.isBuffer(req.body) && req.body.length > 0 ? new Uint8Array(req.body) : null,
    }),
  );
  res.status(response.status);
  response.headers.forEach((value, name) => res.setHeader(name, value));
  res.send(Buffer.from(await response.arrayBuffer()));
});
```

Rate limiting is not handled here: apply it in your framework or reverse proxy, on `POST` above all — the widget calls it from anonymous browsers.

## Options

| Option | Type | Default | What it does |
|---|---|---|---|
| `store` | `SitepingStore` | — | Required. [Prisma](/docs/adapters/prisma), [Drizzle](/docs/adapters/drizzle), [memory](/docs/adapters/memory) or [your own](/docs/adapters/writing-an-adapter) |
| `apiKey` | `string` | — | Enables Bearer auth. Requests send `Authorization: Bearer <key>` |
| `publicEndpoints` | `SitepingHttpMethod[]` | `["POST", "OPTIONS"]` when `apiKey` is set | Methods that skip auth. **Passing a value replaces the default** — include `"POST"` yourself or the widget can no longer submit |
| `requireAuthForDestructive` | `boolean` | `true` | Without an `apiKey`, PATCH and DELETE answer `401`. In `NODE_ENV=production` the factory refuses to start without an `apiKey`. `false` lifts both, production included: PATCH and DELETE, `deleteAll` too, are then open to anyone — only behind your own auth |
| `redactUnauthenticatedEmails` | `boolean` | `true` | See [what responses expose](#what-responses-expose) |
| `access` | `SitepingAccessControl` | — | Your own authentication instead of the four options above — see [custom access](#custom-access) |
| `allowedOrigins` | `string[]` | — | Exact-match CORS allowlist. **No wildcard support** — `["*"]` matches nothing; unset means no CORS headers at all. Listed origins may send `Content-Type`, `Authorization`, and any custom header their preflight asks for (e.g. from the widget's `headers` option) |
| `maxBodyBytes` | `number` | 4 MiB | Largest request body, in bytes — twice the largest submission the validation accepts. A longer one answers `413` before any of it is parsed |
| `webhooks` | `WebhookConfig \| WebhookConfig[]` | — | Fire on each new feedback — see [webhooks](#webhooks) |
| `waitUntil` | `(promise) => void` | — | Keeps webhook deliveries alive after the response on serverless and edge runtimes — see [webhooks](#webhooks) |
| `beforeCreate` | `(input, context) => input` | — | Rewrite a submission before it is stored — see [extension points](#extension-points) |
| `beforeComment` | `(input, context) => input` | — | The same for a [thread](/docs/comments) reply |
| `presentFeedback` | `(feedback, context) => feedback` | — | Transform each record before it is sent |
| `hooks` | `SitepingLifecycleHooks` | — | `onCreated`, `onUpdated`, `onDeleting`, `onDeleted` |
| `logger` | `{ error(message, context) }` | `console.error` | Where unexpected failures go, with the request's method and path — and for a failed hook, the feedback or deletion it concerns. Webhook failures go to their own [`onError`](#webhooks) instead. A logger that throws or rejects falls back to `console.error` |
| `describeError` | `(error) => string \| undefined` | — | The message of a `500` instead of `"Internal server error"`, e.g. a "run your migrations" hint. Never return the error's own details |

`logger.error(message, context)` takes console's and winston's order. [pino](https://getpino.io) takes the context first, and serializes an error only under `err`: passed as is, it type-checks, then logs the message without its context. Adapt it:

```ts
import pino from "pino";

const log = pino();

createSitepingHandler({
  store,
  logger: { error: (message, { error, ...context }) => log.error({ err: error, ...context }, message) },
});
```

## The security model, honestly

- **Reads are public by default.** Without an `apiKey`, anyone who knows the URL can list feedbacks (with emails redacted — see below).
- **Destructive calls are not.** PATCH and DELETE answer `401` unless you set an `apiKey` or explicitly opt out with `requireAuthForDestructive: false`. In production the factory throws at startup rather than run without a key, unless you opted out. That check reads `process.env.NODE_ENV`, so it only runs where `process` exists; elsewhere the `401` still applies.
- `OPTIONS` is always public — preflights must work.
- **Cross-project checks need the store.** PATCH and DELETE verify that the record belongs to the `projectName` they name through the store's optional `verifyProjectOwnership` — every bundled store and anything built on `createCollectionStore` implements it. A hand-written store that omits it skips the check: any caller who knows a feedback `id` can then modify it regardless of `projectName`, so implement the method (see [writing an adapter](/docs/adapters/writing-an-adapter#project-ownership)) or put the endpoint behind an `apiKey`.

### What responses expose

- `clientId` is stripped from **every** response, on feedbacks and on their comments.
- `authorEmail` is blanked unless the request carries a valid `Authorization: Bearer` header — on feedbacks and on the comments of their [threads](/docs/comments). The one exception: a successful `POST` echoes the email back to its author.

Under [`access`](#custom-access), `canReadAuthorEmail` decides instead, for every response — `POST` included.

### What each requester may do

Every feedback in a response — the list, the `PATCH` answer, the `POST` answer — carries `permissions`, and every list carries `permissions.canDeleteAll`:

```json
{ "permissions": { "canChangeStatus": false, "canDelete": false, "canComment": true, "canDeleteComment": false } }
```

They say what this requester would be allowed to do, so the [widget](/docs/widget/configuration#reviewer-mode) and the [dashboard](/docs/dashboard#read-only-and-permissions) hide the rest instead of offering a button that answers `401` or `403`. The server still checks every request.

- Under the `apiKey` policy, an action is allowed when its method is: the key holder may do everything, and a visitor without it what `publicEndpoints` opens. With `["GET", "POST", "OPTIONS"]`, the usual setting for a public widget, a visitor reads and replies but cannot change a status or delete.
- Under [`access`](#custom-access), `authorize` decides, per feedback.

Servers that predate them send none, and neither does store mode: clients then hide nothing.

## Custom access

A shared key suits a site and its dashboard. When reviewers log in, pass `access` instead: the handler asks your code who is calling and what they may do, from the standard `Request` — a session cookie, a JWT, a header set by your proxy. Recipes follow for [OpenID Connect](#recipe-openid-connect) providers and [Better Auth](#recipe-better-auth).

```ts
export const { GET, POST, PATCH, DELETE, OPTIONS } = createSitepingHandler({
  store,
  allowedOrigins: ["https://client-site.com"],
  access: {
    // null (or anything falsy) → 401
    authenticate: (request) => getSessionUser(request),
    // false → 403
    authorize: ({ principal, action, projectName }) =>
      action === "create" || principal.projects.includes(projectName),
    // reviewer emails are personal data
    canReadAuthorEmail: (principal) => principal.isStaff,
  },
});
```

- **`authenticate`** runs on every method but `OPTIONS`, and resolves **who** is calling — an object, a string or a number, never a boolean. Anything falsy (`null`, `undefined`, `""`, `0`) answers `401`. A `true`/`false` check is a type error, and a plain-JavaScript `false` answers `401` too. Its return type types `principal` everywhere else.
- **`authorize`** receives the `action` (`create`, `list`, `update`, `delete`, `deleteAll`, and `createComment` / `deleteComment` for [threads](/docs/comments)), the `projectName` and, for `update`, `delete` and the comment actions, the `feedbackId` — plus the `commentId` for `deleteComment`. It defaults to letting every authenticated caller through. PATCH and DELETE address records by id, so the factory refuses to start with an `authorize` over a store that lacks `verifyProjectOwnership` — every bundled store has it.
- **`authorize` also fills in [`permissions`](#what-each-requester-may-do)**, asked with `dryRun: true`: `update`, `delete`, `createComment` and `deleteComment` for each feedback a response carries, and `deleteAll` once per list. Nothing is being done then — skip your audit log on dry runs. A dry-run `deleteComment` carries no `commentId`, its answer covering the whole thread: a per-author rule answers `false` there (`if (!commentId) return false`). Keep it fast: a page of 50 feedbacks takes 201 dry runs, 8 at a time — they share the response's `request`, so a policy that queries a database can cache per request, in a `WeakMap` keyed on it.
- **A dry run is asked about an action, not a method.** Its `request` is the response's — a `GET` for a list, the `POST` or `PATCH` a write answers — and `authenticate` is not called again for it. Decide by `action`, never by `request.method`; and when `authenticate` admits visitors on some methods only, have `authorize` refuse them the other actions, or they are offered controls that answer `401`.
- **`canReadAuthorEmail`** reveals reviewer emails on `true` only: without it, every response blanks them, and so does any other answer — `undefined` from a principal that lacks the flag you read included. A policy that serves the public widget resolves a principal for anonymous visitors too, so being authenticated says nothing about who may read them.
- **`canCommentAsTeam`** decides whether a comment that asks for the `team` role keeps it; any other is stamped `client`. It defaults to the `canReadAuthorEmail` answer, so a policy that sets neither never grants it — see [who speaks as the team](/docs/comments#who-speaks-as-the-team). Once set, only `true` grants the role.
- A callback that throws answers a logged `500` — except `authorize` on a dry run: that permission is refused, the failure logged, and the response goes out.

`access` replaces `apiKey`, `publicEndpoints`, `requireAuthForDestructive` and `redactUnauthenticatedEmails`: passing both is a type error. From a page on another origin, send the credential through the widget's `headers` option — the widget does not send cookies cross-origin.

### CSRF protection

A browser attaches cookies to a forged cross-site request too, so under `access`, `POST`, `PATCH` and `DELETE` pass two checks before anything else runs:

- **JSON only.** A body without `Content-Type: application/json` answers `415`. That type forces a CORS preflight, which a foreign page fails.
- **Origin.** With `allowedOrigins`, a mutation whose `Origin` is neither listed nor the endpoint's own answers `403` and is logged. Requests without `Origin` — server-to-server calls, curl — pass. Behind a proxy that rewrites the request URL, list your public origin too, or same-origin calls look foreign.

Lists are also sent with `Cache-Control: no-store`, since they depend on who asks. The `apiKey` policy needs neither: its key travels in a header no forged request can set.

### Recipe: OpenID Connect

When reviewers sign in with an OpenID Connect provider — Keycloak, Microsoft Entra ID, Auth0, Zitadel… — the widget and the dashboard send its access token as a bearer, and `access` verifies it with [jose](https://github.com/panva/jose). Visitors without a token keep the public widget: they submit, read and reply, while administrators alone triage and read reviewer emails. If your app signs them in to that provider through Better Auth, use the [Better Auth recipe](#recipe-better-auth) instead.

```ts
// lib/siteping-access.ts
import type { SitepingAccessControl } from "@siteping/server";
import { createRemoteJWKSet, errors, type JWTPayload, jwtVerify } from "jose";

// Both from https://id.example.com/realms/acme/.well-known/openid-configuration
const ISSUER = "https://id.example.com/realms/acme";
const jwks = createRemoteJWKSet(new URL(`${ISSUER}/protocol/openid-connect/certs`));

export interface Reviewer {
  sub: string; // "" for a visitor without a token
  name: string;
  email: string;
  isAdmin: boolean;
}

const VISITOR: Reviewer = { sub: "", name: "", email: "", isAdmin: false };

// Where your provider puts roles: Keycloak's realm roles here — see the table below.
function rolesOf(payload: JWTPayload): unknown {
  return (payload.realm_access as { roles?: unknown } | undefined)?.roles;
}

// The key set down, slow or garbled: an outage, not a bad token.
const KEY_SET_FAILURES = new Set(["ERR_JOSE_GENERIC", "ERR_JWKS_TIMEOUT", "ERR_JWKS_INVALID"]);

export const oidcAccess: SitepingAccessControl<Reviewer> = {
  async authenticate(request) {
    const authorization = request.headers.get("Authorization") ?? "";
    // Only a bearer is a credential: HTTP Basic on a staging site stays a visitor.
    if (!/^Bearer(\s|$)/i.test(authorization)) return VISITOR;
    const token = /^Bearer (\S+)$/i.exec(authorization)?.[1];
    if (!token) return null;
    try {
      const { payload } = await jwtVerify(token, jwks, {
        issuer: ISSUER,
        audience: "siteping-api", // your API's, never the client id
        algorithms: ["RS256", "PS256", "ES256", "EdDSA"],
        requiredClaims: ["exp"],
      });
      if (!payload.sub) return null;
      const roles = rolesOf(payload);
      return {
        sub: payload.sub,
        name: typeof payload.name === "string" ? payload.name : "",
        email: payload.email_verified === true && typeof payload.email === "string" ? payload.email : "",
        isAdmin: Array.isArray(roles) && roles.includes("siteping-admin"),
      };
    } catch (error) {
      if (error instanceof errors.JOSEError && !KEY_SET_FAILURES.has(error.code)) return null; // → 401
      throw error; // → logged 500
    }
  },
  authorize: ({ principal, action }) =>
    principal.isAdmin || action === "create" || action === "list" || action === "createComment",
  canReadAuthorEmail: (principal) => principal.isAdmin,
};
```

```ts
// app/api/siteping/route.ts
export const { GET, POST, PATCH, DELETE, OPTIONS } = createSitepingHandler({
  store,
  // Every site the widget runs on, and the dashboard's own origin.
  allowedOrigins: ["https://client-site.com", "https://inbox.example.com"],
  access: oidcAccess,
  // A signed-in author's name, and verified email, come from the token…
  beforeCreate: (input, { principal }) => ({
    ...input,
    authorName: principal.name || input.authorName,
    authorEmail: principal.email || input.authorEmail,
  }),
  // …on their replies too.
  beforeComment: (input, { principal }) => ({
    ...input,
    authorName: principal.name || input.authorName,
    authorEmail: principal.email || input.authorEmail,
  }),
});
```

On the client, `headers` runs before every request, so it always sends the current token — refreshed, or gone after a sign-out:

```ts
async function headers(): Promise<Record<string, string>> {
  const token = await getAccessToken(); // from your OIDC client library
  return token ? { Authorization: `Bearer ${token}` } : {};
}

initSiteping({ endpoint: "https://api.example.com/api/siteping", projectName: "acme", headers });
// Dashboard, on https://inbox.example.com:
// <SitepingInbox endpoint="https://api.example.com/api/siteping" projects="acme" headers={headers} />
```

- **An access token, never an ID token.** `audience` is the identifier your provider puts in `aud` for your API — Auth0's API identifier, or the audience a Keycloak audience mapper adds. An ID token is addressed to your client application instead, so it answers `401`. Auth0 issues a JWT access token only for an API audience, and Zitadel only when the application's token type is JWT.
- **No bearer, a visitor; a bad one, a `401`.** Without a `Bearer` token the request is anonymous, so the public widget keeps working — also behind HTTP Basic auth, whose credentials a staging site's browser or proxy attaches to every request. A malformed, expired, forged or foreign token answers `401` instead of being downgraded to a visitor: a reviewer whose session lapsed sees it, and the client can refresh the token.
- **An unreachable provider, a `500`.** When the key set cannot be fetched — network error, timeout, non-`200` answer, no key set in it — `authenticate` throws: the handler logs it and answers `500` rather than calling every token invalid. Visitors, who send none, are unaffected. jose caches the keys and refetches them for an unknown `kid`, so key rotation needs nothing.
- **Pinned algorithms, over HTTPS.** `algorithms` lists what your provider signs with, so an unsigned or `HS256` token is refused before any key is looked up. Keep the issuer and the key set on `https://`: whoever can tamper with the key set can mint administrator tokens.
- **The author comes from the token.** `beforeCreate` stamps its name, and its email only when `email_verified` is true; otherwise the widget's values stay. `beforeComment` does the same for replies, so no one signed in replies under another reviewer's name. Access tokens don't always carry these claims, so pass [`identity`](/docs/widget/configuration) to spare signed-in users the widget's identity prompt.
- **Emails stay with administrators.** Since `canReadAuthorEmail` is set, it also decides [who speaks as the team](/docs/comments#who-speaks-as-the-team): administrators' replies are marked `team`, everyone else's `client`.
- **One role, every project.** This `authorize` never reads `projectName`: `siteping-admin` triages every project the endpoint serves, and anyone — visitor or member — lists any of them, screenshots and diagnostics included. To keep several clients apart, give each project its own role, such as `siteping-admin:acme`: keep the caller's roles in the principal, and have `authorize` test `` roles.includes(`siteping-admin:${projectName}`) `` where it tests `isAdmin`. `canReadAuthorEmail` is not told the project, so keep it for a role that covers them all. To put reads behind sign-in too, return `null` instead of `VISITOR` when no bearer comes — every request then needs a token, submissions included — and allow `list` on the caller's projects only.

Roles are provider-specific, so `rolesOf` is yours to write:

| Provider | Roles in the access token | `rolesOf(payload)` returns |
|---|---|---|
| Keycloak | `realm_access.roles` (realm roles), `resource_access.<client>.roles` (client roles) | As above |
| Microsoft Entra ID | `roles` (app roles) | `payload.roles` |
| Auth0 | None by default: add a claim in a post-login Action, e.g. `https://siteping.example/roles` | `payload["https://siteping.example/roles"]` |
| Zitadel | `urn:zitadel:iam:org:project:roles`, an object keyed by role | `Object.keys(payload["urn:zitadel:iam:org:project:roles"] ?? {})` |
| Better Auth ([jwt plugin](#from-another-origin)) | `role`, comma-separated | `typeof payload.role === "string" ? payload.role.split(",") : []` |

#### Letting authors delete their own feedback

The store records no owner: keep your own table, filled by `onCreated`, which sees the principal, and read by `authorize`. A list asks about every feedback it carries — 50 `delete` dry runs for a page of 50 — so read the caller's ids once per request, in a `WeakMap` keyed on it:

```ts
const ownerships = new WeakMap<Request, Promise<Set<string>>>();

/** The ids `sub` submitted, read once per request. */
function submittedBy(request: Request, sub: string): Promise<Set<string>> {
  let ids = ownerships.get(request);
  if (!ids) {
    ids = db.feedbackOwner
      .findMany({ where: { sub }, select: { feedbackId: true } })
      .then((rows) => new Set(rows.map((row) => row.feedbackId)));
    ownerships.set(request, ids);
  }
  return ids;
}

export const { GET, POST, PATCH, DELETE, OPTIONS } = createSitepingHandler({
  store,
  // …allowedOrigins, beforeCreate and beforeComment as in route.ts above
  access: {
    ...oidcAccess,
    authorize: async ({ principal, action, feedbackId = "", request }) =>
      principal.isAdmin ||
      action === "create" ||
      action === "list" ||
      action === "createComment" ||
      (action === "delete" && principal.sub !== "" && (await submittedBy(request, principal.sub)).has(feedbackId)),
  },
  hooks: {
    onCreated: async (feedback, { principal }) => {
      if (principal.sub) await db.feedbackOwner.create({ data: { sub: principal.sub, feedbackId: feedback.id } });
    },
  },
});
```

`onCreated` never fails a submission: if its write fails, that author just cannot delete the feedback. A `sub` is unique per issuer only — with several providers, key the table on both — and `onDeleted` is the place to drop rows.

### Recipe: Better Auth

When your app signs users in with [Better Auth](https://www.better-auth.com), `access` asks it for the session: the widget and a `<SitepingInbox />` mounted in the app send its cookie with every request, so the client side needs no token. Its [admin plugin](https://www.better-auth.com/docs/plugins/admin) tells administrators apart — they triage and read reviewer emails — while everyone else, signed in or not, submits, reads and replies.

This also covers an app that signs users in to an OpenID Connect provider — Keycloak, Microsoft Entra ID, Auth0… — through Better Auth's [Generic OAuth](https://www.better-auth.com/docs/plugins/generic-oauth) or [SSO](https://www.better-auth.com/docs/plugins/sso) plugin: those users hold a Better Auth session too. Keep the [OpenID Connect recipe](#recipe-openid-connect) for access tokens the endpoint verifies itself.

```ts
// lib/auth.ts — your Better Auth server
import { betterAuth } from "better-auth";
import { admin } from "better-auth/plugins";

export const auth = betterAuth({
  // …database, emailAndPassword, socialProviders as you have them
  plugins: [admin()],
});
```

```ts
// lib/siteping-access.ts
import type { SitepingAccessControl } from "@siteping/server";
import { auth } from "@/lib/auth";

export interface Reviewer {
  id: string; // "" for a visitor without a session
  name: string;
  email: string;
  isAdmin: boolean;
}

const VISITOR: Reviewer = { id: "", name: "", email: "", isAdmin: false };

export const betterAuthAccess: SitepingAccessControl<Reviewer> = {
  async authenticate(request) {
    const session = await auth.api.getSession({
      headers: request.headers,
      // Read from the database, never renewed here — see below.
      query: { disableCookieCache: true, disableRefresh: true },
    });
    // No session: a visitor — unless the request sent a bearer token, which then answers 401.
    if (!session) return /^Bearer(\s|$)/i.test(request.headers.get("Authorization") ?? "") ? null : VISITOR;
    const { user } = session;
    return {
      id: user.id,
      name: user.name,
      email: user.emailVerified ? user.email : "",
      // The admin plugin stores several roles comma-separated.
      isAdmin: user.role?.split(",").includes("admin") ?? false,
    };
  },
  authorize: ({ principal, action }) =>
    principal.isAdmin || action === "create" || action === "list" || action === "createComment",
  canReadAuthorEmail: (principal) => principal.isAdmin,
};
```

```ts
});
```

The session also spares signed-in users the widget's identity prompt: pass it as [`identity`](/docs/widget/configuration). The widget reads `identity` once, at init, so key the component on the account — a sign-in or a sign-out then remounts it:

```tsx
// app/feedback.tsx — mounted in your root layout
"use client";
import type { Identity } from "@siteping/widget";
import { useSiteping } from "@siteping/widget/react";
import { authClient } from "@/lib/auth-client"; // createAuthClient() from "better-auth/react"

function Widget({ identity }: { identity: Identity | undefined }) {
  useSiteping({ endpoint: "/api/siteping", projectName: "acme", identity });
  return null;
}

export function Feedback() {
  const { data: session, isPending } = authClient.useSession();
  if (isPending) return null;
  const user = session?.user;
  return <Widget key={user?.id ?? "visitor"} identity={user && { name: user.name, email: user.email }} />;
}
```

- **No session, a visitor; a dead token, a `401`.** Without a session the request is anonymous, so the public widget keeps working — also for someone whose cookie outlived a sign-out, an expiry or a ban, since the browser keeps sending it. A request whose `Bearer` token opens no session answers `401` instead: its client sent the token on purpose, and learns it no longer works. Any other `Authorization` stays a visitor: on a staging site behind HTTP Basic auth, the browser or the proxy attaches those credentials to every request.
- **A database outage, a `500`.** When Better Auth cannot read its sessions, `getSession` throws: the handler logs it and answers `500` rather than downgrading everyone to a visitor. Visitors without a session cookie never reach the database.
- **Read, never renewed.** A session older than Better Auth's `updateAge` gets renewed by the next `getSession`, which writes a later expiry and sets a new cookie — on a response SitePing never sends, so the browser's cookie would expire first. `disableRefresh` leaves the renewal to your app's own requests.
- **A demotion applies at once.** With Better Auth's `session.cookieCache` on, `getSession` trusts the cached cookie until its `maxAge`: a role change or a revoked session would wait for it. `disableCookieCache` reads your `database` or `secondaryStorage` instead, as `getSession` does anyway without the cache. Without either, Better Auth is stateless and the signed cookie is the only session record: another instance — a serverless invocation, a replica — finds no session behind that flag, and serves your administrators as visitors. Drop `disableCookieCache` there; a demotion then waits for the cookie's `maxAge`.
- **Administrators by role.** `isAdmin` reads the admin plugin's `role` — `setRole` with `["user", "admin"]` stores `"user,admin"`. The plugin's `adminUserIds` opens its own endpoints to users whatever their role: give those users the `admin` role too. To let someone triage without the plugin's user management, give them a role of your own (declared in the plugin's `roles`, if you configured some) and test that one.
- **The author comes from the session.** `beforeCreate` stamps the user's name, and their email once `emailVerified` is true; otherwise the widget's value stays. `beforeComment` does the same for replies.
- **Emails stay with administrators.** Since `canReadAuthorEmail` is set, it also decides [who speaks as the team](/docs/comments#who-speaks-as-the-team): administrators' replies from the inbox are marked `team`, everyone else's `client`.
- **Cookies, and CSRF.** A browser attaches the session cookie to a forged cross-site request too; the [CSRF checks](#csrf-protection) stop those, with nothing to configure.
- **One role, every project.** As in the OpenID Connect recipe, `admin` triages every project the endpoint serves and anyone lists any of them. To keep several clients apart, load the caller's projects in `authenticate` — for instance the slugs of their organizations, with Better Auth's organization plugin — and have `authorize` check `projectName` against them. To put reads behind sign-in too, return `null` instead of `VISITOR` — every request then needs a session, submissions included.
- **Authors deleting their own feedback.** The OpenID Connect recipe's [owner table](#letting-authors-delete-their-own-feedback) works as is, with `principal.id` where it reads `principal.sub` — a Better Auth user id is unique in your app, so one column is enough.

#### From another origin

On another origin — the widget on a client's site — a page reaches your app without its cookie: the widget sends cookies to its own origin only. Add Better Auth's [bearer plugin](https://www.better-auth.com/docs/plugins/bearer) and send the session token with `headers`; the recipe needs no change, since the plugin turns the token back into the session `getSession` reads.

```ts
// lib/auth.ts
import { admin, bearer } from "better-auth/plugins";

export const auth = betterAuth({
  // …
  plugins: [admin(), bearer()],
  trustedOrigins: ["https://client-site.com"], // where users sign in from
});

// app/api/siteping/route.ts
export const { GET, POST, PATCH, DELETE, OPTIONS } = createSitepingHandler({
  store,
  // Every site the widget runs on. The inbox stays on the endpoint's own origin.
  allowedOrigins: ["https://client-site.com"],
  access: betterAuthAccess,
  // …beforeCreate and beforeComment as above
});
```

The token arrives in the `set-auth-token` header of the sign-in response; the plugin's documentation shows how to keep it. On the page, `headers` sends it with every request, and `onError` drops it once it stops working:

```ts
function headers(): Record<string, string> {
  const token = localStorage.getItem("bearer_token"); // where your auth client keeps it
  return token ? { Authorization: `Bearer ${token}` } : {};
}

initSiteping({
  endpoint: "https://app.example.com/api/siteping",
  projectName: "acme",
  headers,
  onError: (error) => {
    // A dead token, not a 403 refusal: drop it, and the next request goes out as a visitor.
    if ((error as { status?: number }).status === 401) localStorage.removeItem("bearer_token");
  },
});
```

- **The token is the whole session.** It is the session cookie's value, not a SitePing credential: it opens every Better Auth endpoint of your app, the admin plugin's included, from any origin, and whoever holds it keeps it alive, since Better Auth renews the session as it is used. Kept in `localStorage`, it is readable by every script on that page. So have administrators triage from the inbox mounted in your app, which sends the cookie, out of scripts' reach, and keeps their session on your origin; keep the bearer for reviewers who sign in on the client's site.
- **Drop it once it stops working.** A stale cookie stays a visitor, but a dead token answers `401` to every request, submissions included, and nothing removes it from `localStorage` when the session expires or is revoked. Remove it on a `401`, as above, and when the user signs out — not on every `AUTH` error: a `403` means `authorize` refused that request, a project the reviewer isn't a member of, and the token still opens their session in your app.

When the SitePing endpoint runs apart from Better Auth — another service, an edge worker away from your database — verify tokens from Better Auth's [jwt plugin](https://www.better-auth.com/docs/plugins/jwt) with the [OpenID Connect recipe](#recipe-openid-connect) instead. The page fetches one from `/api/auth/token` with its session cookie and sends it with `headers`. `ISSUER` and `audience` are your Better Auth URL, unless you set the plugin's `jwt.issuer` and `jwt.audience`; the key set is at `/api/auth/jwks`, and tokens are signed `EdDSA`. The payload is the user record: `rolesOf` reads `role` (see the table above), administrators hold `admin`, and the email's verification is in `emailVerified`, not `email_verified`.

## Extension points

```ts
createSitepingHandler({
  store,
  access,
  // Take the author from the session, and scrub tokens pasted in the message.
  beforeCreate: (input, { principal }) => ({
    ...input,
    authorName: principal.name,
    authorEmail: principal.email,
    message: input.message.replace(/token=\S+/g, "token=[redacted]"),
  }),
  // The same for a reply in a thread.
  beforeComment: (input, { principal }) => ({
    ...input,
    authorName: principal.name,
    authorEmail: principal.email,
    body: input.body.replace(/token=\S+/g, "token=[redacted]"),
  }),
  hooks: {
    onCreated: (feedback) => searchIndex.add(feedback),
    // Throw to keep the record: the DELETE answers 502 and can be retried.
    onDeleting: (target) => searchIndex.remove(target),
  },
});
```

- **`beforeCreate`** runs on the validated submission, before `authorize` — which sees the project it returns. **`beforeComment`** does the same for a [reply](/docs/comments), `projectName` and `feedbackId` included — so it runs before the feedback is looked up too, and may run for one that turns out not to exist. The `authorRole` it returns stays a claim, `team` being kept only for a caller [your policy vouches for](/docs/comments#who-speaks-as-the-team). Without it, a reply keeps the name and email its client sent.
- **`presentFeedback`** runs on each record just before it is sent; `clientId` stripping and email redaction still apply after it.
- **`onCreated`**, **`onUpdated`** and **`onDeleted`** are awaited before the response, so serverless runtimes don't cut them off. A throw is logged and never fails the request: the write already happened. `onCreated` runs once per stored feedback, never for a replayed `clientId`.
- **`onDeleting`** runs before the delete, with `{ kind: "single", id, projectName }` or `{ kind: "project", projectName }`. A throw keeps the record and answers `502`.

These callbacks get `{ request, principal }` as their context; `principal` is `null` under the `apiKey` policy. Hooks written as class methods keep their `this`.

To keep one GitHub or GitLab issue per feedback, closed and reopened along with it, [`@siteping/integration-issues`](/docs/issue-trackers) builds these hooks for you.

## HTTP reference

One endpoint, five methods. All bodies are JSON.

| Method | Purpose | Success |
|---|---|---|
| `POST` | Create feedback (widget submissions) — or [a comment](/docs/comments#post-a-comment), when the body has a `feedbackId` | `201` + record. A replayed `clientId` returns the existing record instead of failing (and never notifies webhooks or `onCreated` twice); a `clientId` already used by **another** project is refused with `409` |
| `GET` | List feedbacks, each with its thread and [`permissions`](#what-each-requester-may-do) | `200` + `{ feedbacks, total, capabilities, permissions }`, with `Cache-Control: private, max-age=5` (`no-store` under `access`) |
| `PATCH` | Change a status | `200` + updated record |
| `DELETE` | Delete one or all — or [a comment](/docs/comments#delete-a-comment), when the body has a `commentId` | `200` + `{ deleted: true }` |
| `OPTIONS` | CORS preflight | `204` |

**GET query parameters:** `projectName` (required), `page` (default 1), `limit` (default 50, max 100), `type`, `status`, `statuses` (comma-separated list, max 4 — e.g. `statuses=open,in_progress`), `search`, `url`, `urlPattern`.

**PATCH body:** `{ id, projectName, status }` — all three required. `status` is one of `open`, `in_progress`, `resolved`, `wont_fix`. The server derives `resolvedAt` automatically: set when the status is closed (`resolved`/`wont_fix`), cleared otherwise.

**DELETE body:** `{ id, projectName }` for one record, or `{ projectName, deleteAll: true }` for everything in the project.

**Errors:** invalid JSON → `400 { error }`; validation failure → `400 { errors: [{ field, message }] }`, the first 20 issues; a body over `maxBodyBytes` → `413`; missing or wrong credentials → `401`; refused by `authorize` or a CSRF check → `403`; not JSON under `access` → `415`; unknown id → `404`; `clientId` owned by another project, a comment's `clientId` already used on another feedback, or a full comment thread → `409 { error }`; a value longer than the store holds (a `VARCHAR(191)` column on MySQL) → `422 { error }`; comment write on a store without comments → `501 { error }`; `onDeleting` threw → `502`; anything else → `500 { error: "Internal server error" }`, or the message `describeError` returns.

### Validation limits worth knowing

The whole body ≤ `maxBodyBytes` (4 MiB) · `message` ≤ 5000 chars · `annotations` ≤ 50 per feedback · comment `body` ≤ 5000 chars, 100 comments per thread · `screenshotDataUrl` ≤ 1.5 MB, JPEG/PNG/WebP only · `diagnostics` ≤ 50 console + 20 network entries · `clientId` matches `[a-zA-Z0-9_-]+` · `authorEmail` matches the same Unicode-aware pattern as the widget's identity modal (`françois@exemple.fr` is fine), so an address the modal accepts is never rejected here.

## Webhooks

Get pinged on every new feedback:

```ts
createSitepingHandler({
  store,
  webhooks: [
    { url: process.env.SLACK_WEBHOOK_URL!, type: "slack" },
    { url: "https://my-api.dev/hooks/siteping", type: "generic", headers: { "x-secret": "…" } },
  ],
});
```

`type` is `"slack"`, `"discord"`, or `"generic"` (default — posts the record as JSON with the author's email unredacted, so treat generic webhook targets as trusted; `clientId` is stripped like everywhere else, from its comments too, and `GenericWebhookPayload` types the body as the receiver parses it, dates as ISO strings). Each call has a 5-second timeout by default — set `timeoutMs` per webhook, a positive integer up to 2,147,483,647, the longest delay a timer holds; the factory throws on any other value. Failures never block the submission, and an optional `onError(err, feedbackId)` lets you log them — an async one is awaited, and its own failure is reported to `console.warn`. A replayed `clientId` never fires them again, and two overlapping submissions of the same `clientId` (the widget retrying a request that timed out) notify once when they reach the same server process. Across several instances only the store can tell them apart: Prisma's `@unique` on `clientId` does, and so does the unique index of the [Drizzle store](/docs/adapters/drizzle). The memory and localStorage stores, like any store built on `createCollectionStore`, deduplicate only within one store instance, and a custom store that returns the existing record on a duplicate may notify twice unless it implements `createFeedbackIfAbsent` atomically — see [Writing an adapter](/docs/adapters/writing-an-adapter#exactly-once-creation-effects).

Deliveries are not awaited: the widget gets its answer first. A serverless or edge runtime may freeze or cancel that work once the response is out, so hand it over with `waitUntil`:

```ts
import { after } from "next/server";

createSitepingHandler({ store, webhooks, waitUntil: after });
```

`waitUntil` from `@vercel/functions` or from `cloudflare:workers` works the same way — pass a standalone function, not an unbound method.

Feedback text is typed by anonymous visitors, so the chat payloads are hardened: Slack text is escaped (a comment containing `<!channel>` is shown literally, never as a notification) and Discord messages are sent with mention parsing disabled (`allowed_mentions: { parse: [] }`) and their markdown escaped (a `[Reset your password](https://…)` masked link is shown as typed, never as a disguised link) — a public form can't be used to ping your whole server or phish it. Long values are truncated to Slack's and Discord's size limits (after escaping), so a 2000-character page URL never gets the whole notification rejected.
