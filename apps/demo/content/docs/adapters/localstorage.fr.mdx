---
title: Adapter localStorage
description: Un store côté client — toute la boucle de feedback dans le navigateur, sans serveur.
---

`@siteping/adapter-localstorage` persiste les feedbacks dans le navigateur du visiteur. Combiné à l'option `store` du widget, vous obtenez une boucle de feedback complète sans aucun backend — idéal pour les démos, les prototypes et les sites de documentation (ce site l'utilise).

```bash
npm i @siteping/adapter-localstorage
```

```ts
import { initSiteping } from "@siteping/widget";
import { LocalStorageStore } from "@siteping/adapter-localstorage";

initSiteping({
  store: new LocalStorageStore(),
  projectName: "ma-demo",
});
```

## Options

| Option | Type | Défaut | Ce que ça fait |
|---|---|---|---|
| `key` | `string` | `"siteping_feedbacks"` | L'unique clé localStorage contenant tout le tableau de feedbacks |

## Notes de comportement

- **Les données restent sur une seule machine.** Chaque visiteur ne voit que ses propres feedbacks — c'est voulu. Rien ne quitte le navigateur.
- **Des données corrompues ne font jamais planter — et ne sont jamais perdues en silence.** Un enregistrement sans `annotations` est lu avec une liste vide, et une entrée illisible est ignorée sans masquer les autres ; un JSON stocké impossible à analyser se lit comme une liste vide. Avant que la prochaine écriture ne remplace un contenu qui n'a pas pu être lu entièrement, le contenu brut est copié sous `<key>.corrupt` (par ex. `siteping_feedbacks.corrupt`) ; si cette copie échoue, l'écriture échoue avec une `StorePersistenceError` à la place.
- **Sous pression de quota, les captures sautent en premier.** Si une écriture dépasse le quota de stockage du navigateur (~5 Mo par origine), l'adapter réessaie une fois sans la capture avant d'abandonner avec une `StorePersistenceError` — le commentaire survit même quand l'image ne peut pas.
- **Les actions en masse sont sûres dans un même onglet.** Le store applique ses écritures une par une : sélectionner plusieurs feedbacks puis les résoudre ou les supprimer ensemble les modifie tous. La garantie s'arrête à l'instance : deux onglets — ou deux `LocalStorageStore` sur la même `key` — réécrivent chacun le tableau entier, et la dernière écriture l'emporte.
- **Les dates survivent à l'aller-retour** — `createdAt` et consorts reviennent en vrais objets `Date`, pas en chaînes.
- **Compatible SSR là où ça compte :** les lectures et écritures se dégradent proprement sans `localStorage`. La seule exception est `clear()`, qui suppose un navigateur — ne l'appelez que côté client.
- Les envois avec un `clientId` en double renvoient l'enregistrement existant, comme pour tous les autres adapters.
